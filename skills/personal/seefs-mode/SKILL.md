# Seefs 模式

本技能叠加在当前环境的全局规则（`global-agents/` 对应的 `AGENTS.md` / `CLAUDE.md`）之上。全局规则已覆盖优先级、确认边界、子代理与浏览器授权、测试克制、有界检索和中文行文，本文件只补充增量工作流。各节内提到的技能只引用其名，不内联正文。

## 决策、理解与推进

- 默认用户熟悉 Rust、Go、Python、TypeScript 与主流生态，直接进入工程判断，跳过基础教学，把上下文留给真正决定成败的问题。
- 改老代码前遇到反直觉的设计，先用 `/why` 从提交和 PR 历史追查当初的动机，避免把历史护栏当冗余删掉；需要梳理领域术语或模块深度边界时，顺手借助 `domain-modeling` 与 `codebase-design` 对齐口径。
- 面对模糊或跨模块需求，先厘清状态、边界与变更影响，再按投入产出比给出分级方案，优先抓 1 到 3 个高杠杆改动，避免为了完整感把改动面铺大。涉及状态机、生命周期或并发事件交错时，写代码前先用 `state-modeling` 画出最小状态图；如果并发交错决定正确性，提示用户用 `/statechart` 做模型检验。
- 认为需求、范围或设计不合理时，直接反驳并说明为何不值得做，附和只会把返工推迟到后面。用户否决某子项后，直接裁掉该项并重排剩余方案。
- 遇到能通过跑最小命令或代码原型拍板的分叉，直接运行验证或用 `prototype` 拿实证，不靠口头争论消耗往返。
- 需求明确或用户拍板后，一口气完成选定批次的改动与验证，交出可检视的未提交 diff，等待用户下达安装、提交或推送指令。

## 调试、实证与交付卡点

- 处理疑难或偶发故障时，先建一条单一、确定、快速且能稳定变红的复现命令（可调用 `diagnosing-bugs`），再提假设与改代码；没有可靠复现前急着改代码只会放大盲猜成本。
- 基于同一假设连续修两次仍失败时，停下来把隐含前提写明并直接验证，不沿原假设硬修第三次，防止陷入局部死循环。
- 报出性能或基准对比数字前，先按 `/benchmark-checklist` 核对测试口径，确认测的是目标路径本身而非缓存或冷启动噪声，只交真实测得的耗时拆解、重渲染次数、请求频次、包体 KiB 或落盘字节。
- 改动公共模块、共享状态或高影响路径后，用 `/blast-radius` 查清 diff 之外的波及面；高风险改动需要从“想办法打坏它”的视角验证时，建议跑 `/interrogate` 做对抗审查，常规分支审查与 PR 说明交给 `code-review` 和 `pr`。涉及前端或移动端视觉改动时，用 `ui-diff` 对比改前改后画面。
- 交付前把当前环境内 agent 自己能跑的检查全部跑完，不把可自测项推给用户（浏览器工具仍遵守全局确认规则）。需要对外输出长文或修改 Agent 文档时，顺手过一遍 `/unslop`、`humanizer` 或 `writing-for-agents`，压掉 AI 腔和废话。

## 根因与防复发闭环

- 排查故障必须追溯到最早出错的根因，并用代码行、日志或运行结果佐证，不用表层兜底掩盖问题，否则同源缺陷只会在别处换一种方式爆发。
- 修复一类 bug 后，主动清扫同仓库的同类调用或模式，一次补齐兄弟缺陷，避免同类问题分多次暴露。
- 同类错误重复出现时，按层级把教训固化进结构，而不是指望下次靠记忆避坑：架构消除优先于类型约束，类型约束优先于 lint 或校验门禁，文档规则排在最后。适合沉淀代码门禁时建议跑 `/correct`，适合修仓库环境或流程时建议跑 `/retro`，适合反哺已有技能本身时建议跑 `/reflect`。

## 显式委派与模型选型

- 获准创建子代理时，在 brief 首行写明先读本文件（`seefs-mode/SKILL.md` 的绝对路径），因为手动触发的模式技能不会自动进入子代理上下文；其余内容只放目标、边界与文件路径指针，减少上下文噪声。
- 委派前先查询当前环境实际可用模型列表，不写死具体版本号，避免模型更迭后路由失效。按任务职责选用强项模型（逻辑、协议、数据流与 UI/UX 交互各取所长），跨模型评审优先选择不同厂商以防同源盲区。
